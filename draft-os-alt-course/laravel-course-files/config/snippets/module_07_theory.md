# Модуль 7 — Теория: Контроль целостности файлов в Альт Линукс

---

## 1. Зачем нужен контроль целостности

Представь сценарий: злоумышленник получил кратковременный доступ к серверу и подменил `/usr/bin/sudo` — теперь при каждом вызове `sudo` он перехватывает пароль администратора. Антивирус молчит — файл не вредоносный по сигнатурам, он просто **другой**. Логи в `/var/log` почищены. Внешне всё работает нормально.

Единственный способ это обнаружить — заранее зафиксировать **эталонное** состояние системы и периодически сравнивать с ним текущее. Это и есть **контроль целостности файлов**.

Для ФСТЭК-сертифицированных систем контроль целостности программной среды — **обязательное** требование. **Альт Линукс СП** поставляется с уже настроенными механизмами контроля.

---

## 2. Два уровня контроля целостности в Альт

В Альт Линукс контроль целостности реализован на **двух уровнях**, которые дополняют друг друга.

**Первый уровень — RPM.** Встроен в пакетный менеджер, не требует настройки, работает сразу после установки системы. Проверяет только файлы, установленные из пакетов.

**Второй уровень — Osec.** Отдельный инструмент, требует первоначальной настройки. Проверяет **любые** файлы — конфиги, созданные вручную, скрипты, ключи SSH и всё, что RPM не знает.

Правильный подход — использовать **оба** уровня вместе.

---

## 3. Первый уровень: `rpm -V`

RPM хранит в своей базе (`/var/lib/rpm`) эталонные метаданные всех установленных файлов: хэш, размер, права доступа, владелец. Команда **`rpm -V`** сравнивает текущее состояние файлов с этими эталонами.

### Основные команды

```bash
# Проверить один пакет
rpm -V bash

# Проверить все установленные пакеты
rpm -Va

# Узнать, какому пакету принадлежит файл
rpm -qf /usr/bin/sudo

# Восстановить файлы пакета из RPM-базы
rpm --restore coreutils
```

На части установок **Альт** ключ **`rpm --restore`** может отсутствовать — тогда восстановление выполняют переустановкой пакета (например, **`apt-get install --reinstall имя_пакета`**). Смысл тот же: вернуть файлы к состоянию из пакета.

### Как читать вывод

Если файл не изменился — **строка не выводится**. Если изменился — выводится строка с флагами:

```text
S.5....T.  /usr/bin/sudo
.M.......  /usr/bin/chsh
..5......  /etc/ssh/sshd_config
```

Каждая позиция в строке флагов означает конкретный атрибут. **Точка `.`** на месте флага означает, что атрибут **не** изменился.

| Позиция | Флаг | Что изменилось |
|:-------:|:----:|----------------|
| 1 | **S** | Размер файла (Size) |
| 2 | **M** | Права доступа (Mode) |
| 3 | **5** | MD5-хэш содержимого |
| 4 | **D** | Старший/младший номер устройства |
| 5 | **L** | Путь символической ссылки |
| 6 | **U** | Владелец (User) |
| 7 | **G** | Группа (Group) |
| 8 | **T** | Время модификации (mTime) |
| 9 | **P** | Возможности (capabilities) |

### Пример разбора строки `S.5....T.  /usr/bin/sudo`

- **S** — размер изменился  
- **.** — права не изменились  
- **5** — MD5-хэш не совпадает с эталоном  
- **T** — время модификации изменилось  

**Итог:** содержимое файла подменено.

### Ограничение RPM

RPM знает только о файлах, которые **сам** устанавливал. Всё, что создано вручную — конфиги, SSH-ключи, скрипты в `/etc/cron.d/`, правила в `/etc/sudoers.d/` — **вне** контроля RPM. Именно для этого нужен второй уровень.

---

## 4. Второй уровень: Osec

**Osec** — инструмент контроля целостности из проекта **Openwall**, родной для Альт Линукс. В отличие от `rpm -V`, он контролирует **любые** файлы, которые ты укажешь — независимо от того, установлены ли они из пакетов или нет.

Принцип работы простой: при инициализации Osec обходит указанные каталоги, вычисляет хэши и сохраняет **эталонную базу**. При каждом последующем запуске сравнивает текущее состояние с базой и формирует отчёт об изменениях.

### Установка

```bash
apt-get install osec
```

### Ключевые файлы

| Путь | Назначение |
|------|------------|
| `/etc/osec/` | конфигурация |
| `/var/lib/osec/` | база эталонных хэшей |
| `/var/log/osec/` | отчёты о проверках |

### Конфигурация `/etc/osec/osec.conf`

```bash
# Каталоги для проверки (через пробел)
DIRS="/bin /sbin /usr/bin /usr/sbin /lib /lib64 /etc"

# Каталоги и файлы, которые исключить из проверки
EXCLUDE="/etc/mtab /etc/resolv.conf /etc/adjtime /var/log"

# Email для отправки отчётов
MAIL_TO="admin@company.ru"

# Сколько файлов отчётов хранить
KEEP=5
```

### Почему важно правильно настроить `EXCLUDE`

Некоторые файлы меняются постоянно и **легитимно**: `/etc/resolv.conf` обновляется при смене сети, `/etc/mtab` — при монтировании дисков. Если их не исключить, каждый запуск Osec будет выдавать **сотни ложных** срабатываний, и реальные угрозы утонут в шуме.

### Основные команды

```bash
# Инициализация — создать эталонную базу
# (запускать на чистой настроенной системе до ввода в эксплуатацию)
osec

# Запустить проверку вручную (та же команда, если база уже есть)
osec

# Посмотреть последний отчёт
cat /var/log/osec/osec.log
```

Osec использует **одну команду** и для инициализации, и для проверки: если базы ещё нет — создаёт её; если база есть — сравнивает с ней. Точное поведение и путь к конфигу уточняй по **`man osec`** и документации пакета на своей системе.

### Чтение отчёта Osec

```text
new: /etc/cron.d/backdoor        ← новый файл, которого не было
removed: /bin/ping               ← файл удалён
changed: /etc/passwd             ← файл изменён
  size:  1024 -> 1089
  md5:   a1b2c3d4 -> e5f6a7b8
  mtime: 2025-01-01 12:00 -> 2025-04-23 09:15
```

Каждая строка отчёта — событие, которое требует внимания администратора. **`new`** и **`changed`** в системных каталогах — потенциальный инцидент.

### Интеграция с ЦУС

Это ключевое отличие Osec от аналогов в других дистрибутивах: он управляется через **ЦУС Альт** ([локальный интерфейс ЦУС](https://127.0.0.1:8080), модуль «Проверка целостности»):

- **Периодический запуск** — включить и выбрать расписание  
- **Настройка отчётности** — записывать в журнал и/или отправлять на email  
- **Количество хранимых журналов** — сколько файлов отчётов держать  
- **Ручной запуск** — кнопка «Запустить» для немедленной проверки  
- **Просмотр файлов журнала** — список отчётов с датами и размерами  

### Запуск по расписанию через systemd

```bash
# Osec устанавливает systemd-таймер
systemctl enable osec.timer
systemctl start osec.timer

# Посмотреть расписание
systemctl list-timers 'osec*'

# Посмотреть статус
systemctl status osec.service
```

## 5. Правильный порядок работы

Это **критически важно**: база должна создаваться на **чистой** системе сразу после завершения настройки, **до** ввода в эксплуатацию. Если создать базу на уже работающей или скомпрометированной системе — эталон будет содержать вредоносные изменения, и контроль потеряет смысл.

1. Установка ОС Альт  
2. Настройка системы (пакеты, конфиги, пользователи, службы)  
3. **← здесь:** создать эталонную базу Osec  
4. **← здесь:** включить `osec.timer`  
5. Ввод сервера в эксплуатацию  
6. Периодические проверки по расписанию → отчёты администратору  
7. После плановых изменений (обновление пакетов, смена конфига):  
   - проверить, что изменения легитимны;  
   - запустить Osec заново для **обновления базы**.  

Обновление базы после планового обновления пакетов — **обязательный** шаг. Иначе каждая следующая проверка будет выдавать сотни изменений по обновлённым файлам.

## 6. Что контролировать — список критических файлов

Минимальный набор файлов и каталогов, которые обязательно должны быть под контролем Osec:

```bash
# Исполняемые файлы
/bin
/sbin
/usr/bin
/usr/sbin

# Критические конфиги аутентификации
/etc/passwd
/etc/group
/etc/sudoers
/etc/sudoers.d
/etc/pam.d
/etc/passwdqc.conf

# SSH
/etc/openssh/sshd_config
/etc/openssh/ssh_host_*_key

# Библиотеки
/lib
/lib64
/usr/lib

# Планировщик задач
/etc/cron.d
/etc/cron.daily
/var/spool/cron
```

Список дополняется политикой организации и профилем сервера.

## 7. Сравнение с другими дистрибутивами

| Параметр | Альт Линукс | Ред ОС | Астра Линукс |
|----------|-------------|--------|--------------|
| Встроенный инструмент второго уровня | **Osec** (Openwall) | нет — используют **AIDE** или **Afick** | нет — используют **AIDE** или **Afick** |
| Интеграция с GUI | **ЦУС** — есть модуль | нет | нет |
| Запуск по расписанию | **systemd timer** (из коробки для Osec) | cron (настраивается вручную) | cron (настраивается вручную) |
| Контроль на уровне ядра | нет | нет | **Parsec** (только СЕ-версия и др. — по документации поставщика) |
| `rpm -V` / пакетный эталон | да | да (`dnf verify` и аналоги) | да (`apt` / своя модель — по редакции) |

**Принципиальное отличие Parsec в «Астра» от Osec:** Osec обнаруживает изменения **постфактум** — при следующем плановом запуске. Parsec может **запрещать** запуск изменённых файлов в реальном времени на уровне ядра. Это **разные уровни** защиты.

На практикуме в курсе лабораторная работа модуля 7 выполняется в контейнере с **Osec** и **rpm -V** (см. практику модуля).

## 8. Итог для администратора Альт

**Osec** — первый инструмент, который нужно настроить после развёртывания сервера Альт. Три действия:

```bash
# 1. Установить
apt-get install osec

# 2. Настроить, какие каталоги контролировать
nano /etc/osec/osec.conf

# 3. Создать эталонную базу и включить таймер
osec
systemctl enable --now osec.timer
```

После этого Osec будет автоматически проверять систему по расписанию и сигнализировать об изменениях. Управлять им можно как из командной строки, так и через **ЦУС** — это отличительная особенность Альт по сравнению с типовыми сценариями Ред ОС и «Астра», где чаще опираются на AIDE/Afick и cron без того же уровня интеграции с единой консолью управления.
