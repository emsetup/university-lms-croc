# Polkit, модуль ролей и control

Управление привилегиями приложений в ОС Альт Линукс.

---

## 1. Что такое Polkit и зачем он нужен

В Linux исторически существует жёсткое разделение: обычный пользователь и **root**. Если программе нужны права root, пользователю предлагали ввести пароль root (**`su`**) или настраивали **`sudo`**. Оба подхода грубые: либо всё, либо ничего.

**Polkit** решает другую задачу: он позволяет **непривилегированным** процессам выполнять **конкретные** привилегированные действия **без** предоставления полных прав root. Не «стать root», а «**разрешить конкретное действие** конкретному пользователю в конкретном контексте».

Три типичных сценария:

- пользователь хочет подключиться к **Wi‑Fi** — нужны права для управления сетью, но не весь root;
- пользователь хочет смонтировать **USB**‑флешку — нужны права для работы с устройствами, но не весь root;
- пользователь хочет **перезапустить принтер (CUPS)** — нужны права для управления службой, но не весь root.

Именно для таких случаев существует Polkit. Он управляет **действиями**, а не «уровнем привилегий пользователя» в смысле **`sudo`** — это принципиальное отличие.

### Ключевое отличие от `sudo`

| Параметр | `sudo` | Polkit |
|----------|--------|--------|
| Что делает | Повышает привилегии пользователя до root | Разрешает **конкретное действие** без полного root |
| Гранулярность | Команда целиком | Отдельное **действие** внутри приложения |
| Кто вызывает | Пользователь явно | Приложение **автоматически** при необходимости |
| Конфигурация | `/etc/sudoers` | XML **`.policy`** + JavaScript‑правила |
| Диалог | Запрос пароля в терминале | Графический или консольный диалог агента |

## 2. Архитектура Polkit

Polkit состоит из нескольких компонентов, которые работают вместе.

- **`polkitd`** — системный демон, который принимает решения об авторизации. Запускается как системная служба (в systemd обычно **`polkit`**), работает от имени root.
- **Агент аутентификации** — графический или консольный диалог, который показывается пользователю, когда нужно подтвердить действие паролем. В графическом окружении MATE это диалоговое окно, в консоли — текстовый запрос.

Схема работы:

```text
Приложение (NetworkManager, PackageKit, udisks2…)
  │ запрашивает действие
  ▼
polkitd
  1. Находит действие в /usr/share/polkit-1/actions/
  2. Проверяет правила в /etc/polkit-1/rules.d/
  3. Принимает решение: yes / no / auth_admin
  │
  ├── yes        → разрешить
  ├── auth_admin → запросить пароль администратора
  └── no         → отказать
```

## 3. Действия (actions) — что это и где лежат

**Действие (action)** — описание конкретной привилегированной операции. У каждого действия есть **уникальный идентификатор** в формате обратного доменного имени.

Все действия описаны в XML‑файлах с расширением **`.policy`** в каталоге:

```text
/usr/share/polkit-1/actions/
```

Посмотреть доступные действия:

```bash
ls /usr/share/polkit-1/actions/
```

Типичные имена файлов: `org.freedesktop.NetworkManager.policy`, `org.freedesktop.PackageKit.policy`, `org.freedesktop.UDisks2.policy`, **`org.altlinux.alterator.policy`** и др.

### Структура файла `.policy`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE policyconfig PUBLIC ...>
<policyconfig>
  <action id="org.freedesktop.NetworkManager.network-control">
    <description>Управление сетевыми подключениями</description>
    <message>Для управления сетью требуется аутентификация</message>
    <defaults>
      <allow_any>auth_admin</allow_any>
      <allow_inactive>auth_admin</allow_inactive>
      <allow_active>yes</allow_active>
    </defaults>
  </action>
</policyconfig>
```

### Три контекста пользователя

- **`allow_any`** — запрос от любого пользователя независимо от сессии.
- **`allow_inactive`** — запрос из **неактивной** сессии (SSH, VNC, tmux и т.п.).
- **`allow_active`** — запрос из **активной локальной** сессии (пользователь физически за консолью рабочей станции).

### Возможные значения разрешений

| Значение | Смысл |
|----------|--------|
| `yes` | Разрешить без запроса пароля |
| `no` | Запретить всегда |
| `auth_self` | Запросить пароль **самого пользователя** |
| `auth_admin` | Запросить пароль **администратора (root)** |
| `auth_self_keep` | Запросить пароль пользователя, запомнить на время сессии |
| `auth_admin_keep` | Запросить пароль администратора, запомнить на время сессии |

**Пример.** Почему за компьютером можно переключить Wi‑Fi без пароля, а по SSH — нет: для локальной активной сессии может сработать **`allow_active=yes`**, а для удалённой неактивной — **`allow_inactive=auth_admin`**. Контекст сессии меняет ветку политики.

## 4. Правила (rules) — тонкая настройка

Значения по умолчанию в **`.policy`** задаёт разработчик пакета. Администратор может **переопределить** поведение через **правила**.

Правила пишутся на **JavaScript** и хранятся в:

```text
/etc/polkit-1/rules.d/
```

Файлы правил должны иметь расширение **`.rules`**. Имена с числовым префиксом — обычная практика упорядочивания:

```text
/etc/polkit-1/rules.d/
├── 10-network-managers.rules
├── 50-default.rules
└── 90-restrict-shutdown.rules
```

**Примечание.** Меньший номер в имени файла — выше приоритет: правило из `10-*.rules` обрабатывается раньше, чем из `90-*.rules`. Если правило **вернуло результат** для данного запроса, цепочка для этого запроса **останавливается** (дальнейшие файлы для этого решения не нужны).

### Синтаксис правил

```javascript
polkit.addRule(function(action, subject) {
    // action.id — идентификатор действия
    // subject.user — имя пользователя
    // subject.isInGroup('group') — проверка группы
    // subject.local — true, если локальная сессия
    // subject.active — true, если активная сессия

    // Возвращаемые значения:
    // polkit.Result.YES — разрешить
    // polkit.Result.NO — запретить
    // polkit.Result.AUTH_ADMIN — запросить пароль администратора
    // null (ничего не вернуть) — передать следующему правилу
});
```

## 5. Практические примеры правил

### Группа `netadmins` управляет сетью без пароля

```javascript
// /etc/polkit-1/rules.d/10-netadmins.rules
polkit.addRule(function(action, subject) {
    if (action.id.indexOf('org.freedesktop.NetworkManager') === 0 &&
        subject.isInGroup('netadmins')) {
        return polkit.Result.YES;
    }
});
```

### Разрешить только локальную сессию; по SSH — пароль

```javascript
polkit.addRule(function(action, subject) {
    if (action.id.indexOf('org.freedesktop.NetworkManager') === 0 &&
        subject.isInGroup('netadmins') &&
        subject.active == true &&
        subject.local == true) {
        return polkit.Result.YES;
    }
});
```

### Запретить выключение всем, кроме `wheel`

```javascript
// /etc/polkit-1/rules.d/10-restrict-shutdown.rules
polkit.addRule(function(action, subject) {
    if (action.id === 'org.freedesktop.login1.power-off' ||
        action.id === 'org.freedesktop.login1.reboot') {
        if (subject.isInGroup('wheel')) {
            return polkit.Result.YES;
        }
        return polkit.Result.NO;
    }
});
```

**Важно.** Типичная ошибка безопасности — правило **без проверки `subject`**: если нет **`subject.isInGroup()`** или **`subject.user`**, вы можете непреднамеренно разрешить действие **всем** пользователям.

## 6. Polkit в контексте Альт Линукс

### Polkit и NetworkManager

Из модуля про сеть: в **Альт Линукс** NetworkManager опирается на Polkit, поэтому обычный пользователь может переключать подключения **без** ручного **`sudo`** — решение принимает **polkitd**.

```bash
ls /usr/share/polkit-1/actions/ | grep NetworkManager
```

Ключевые действия NM (примеры): `org.freedesktop.NetworkManager.network-control`, `org.freedesktop.NetworkManager.settings.modify.own`.

### Polkit и ЦУС (Alterator)

**ЦУС** использует Polkit для доступа к административным функциям. Действия ЦУС имеют идентификаторы вида **`org.altlinux.alterator.*`** — так можно настраивать, что пользователи могут делать через ЦУС, не выдавая полный **`sudo`** всем подряд.

### Диагностические команды

```bash
# Посмотреть все действия
pkaction

# Подробная информация о действии
pkaction --action-id org.freedesktop.NetworkManager.network-control --verbose

# Проверить авторизацию для текущего процесса
pkcheck --action-id org.freedesktop.NetworkManager.network-control --process $$

# Выполнить команду через Polkit (на учебной машине; нужно соответствующее действие в политике)
pkexec /usr/bin/apt-get install vim

# Посмотреть события polkitd
journalctl -u polkit --since today

# Перезапустить после изменения правил
systemctl restart polkit
```

На части версий Polkit для **`pkcheck`** нужен явный **`--process`** (см. практику модуля 9).

### Сравнение с другими дистрибутивами

| Параметр | Альт Линукс | РедОС | Астра Линукс |
|----------|-------------|--------|--------------|
| Инструмент | Polkit (стандартный) | Polkit (стандартный) | Polkit + Parsec |
| Интеграция с GUI | ЦУС (Alterator) | Нет аналога | Нет аналога |
| Специфичные действия | `org.altlinux.alterator.*` | `org.redos.*` | `org.astralinux.*` |
| Мандатный контроль | Нет | Нет | Parsec (только СЕ) |
| Переносимость правил | Стандартные JS‑правила | Стандартные JS‑правила | Parsec‑правила не переносимы |

## 7. Три механизма управления привилегиями в Альт Линукс

В **Альт Линукс** рядом стоят **три взаимодополняющих** механизма. Важно понимать, **когда** какой использовать.

| Механизм | Для чего | Уровень | Уникальность |
|----------|----------|---------|----------------|
| **`sudo`** | Запуск команд от root | Команда целиком | Стандарт Linux |
| **Polkit** | Авторизация **действий приложений** | Действие внутри приложения | Стандарт Linux |
| **`control`** | Режимы доступа к **системным утилитам** и связанным объектам | Права на файлы, SUID, конфиги служб | Только Альт Линукс |

---

## 8. Утилита `control` — управление доступом к системным компонентам

**`control`** — механизм переключения между **фиксированными состояниями** безопасности для системных утилит и служб в **Альт Линукс**. В первую очередь полезен для управления **SUID/SGID**‑бинарниками и согласованными режимами. Настраивать **`control`** имеет смысл с учётной записью администратора (root).

В отличие от **`sudo`** и **Polkit**, **`control`** опирается на **права файловой системы** и **скрипты** из **`/etc/control.d/facilities/`**, которые меняют права на исполняемые файлы или параметры служб.

### Просмотр управляемых объектов

```bash
control
```

Пример фрагмента вывода (набор строк зависит от версии и профиля):

```text
at              restricted      (public restricted atdaemon)
crontab         public          (public restricted)
fusermount      restricted      (public wheelonly restricted)
su              wheelonly       (public wheel wheelonly restricted)
sudo            public          (public wheelonly restricted)
```

### Справка по объекту

```bash
control su help
control fusermount help
```

В **`control su help`** обычно перечислены режимы вроде **`public`**, **`wheel`**, **`wheelonly`**, **`restricted`** — точные определения смотрите в выводе **`help`** на вашей системе.

### Переключение состояния

```bash
control su
# пример текущего режима: wheelonly

control su wheel
control su wheelonly
control su restricted
control su public
```

Для **`sudo`** набор режимов задаётся отдельно; пример из практики администрирования **Альт Линукс**:

```bash
control sudowheel enabled
```

**Примечание.** **`control`** — типичная особенность экосистемы **Альт Линукс**; в других дистрибутивах те же цели часто достигают вручную через **`chmod`**, **`chown`** и правки конфигов без единого переключаемого реестра режимов.

## 9. Модуль ролей — группы через `libnss-role` и `/etc/role`

### Задача

**Модуль ролей** (через **`libnss-role`**) — механизм, характерный для **Альт Линукс**: он позволяет связать **роли** и **наборы привилегий** без ручного добавления пользователя в десятки отдельных POSIX‑групп.

В «плоском» POSIX пользователь либо в группе, либо нет. **Роль** в модели **Альт Линукс** — это тоже группа, но она описывает **характер деятельности** (`localadmins`, `users`, `powerusers` и т.д.) и может **наследовать** набор **привилегий** (`cdwriter`, `audio`, `wheel`, `fuse` и т.д.).

### Пример связки

Если в **`/etc/group`** пользователь входит в группу **`users`**, а в **`/etc/role`** задано:

```text
users:cdwriter,audio,fuse,camera
```

то при работающем **`libnss-role`** пользователь получает перечисленные привилегии **без** явного членства в каждой из этих групп в **`/etc/group`**. Вложенность ролей и точное поведение зависят от версии и конфигурации — сверяйте с **`man`** и документацией дистрибутива.

### Установка и включение

```bash
apt-get install libnss-role
control libnss-role enabled
control libnss-role
# ожидаемо: enabled
```

### Файл `/etc/role`

Формат строки:

```text
роль:привилегия1,привилегия2,привилегия3
```

Пример фрагмента:

```text
localadmins:wheel,remote,vboxusers,vboxadd
powerusers:remote,vboxadd,vboxusers
users:cdwriter,cdrom,audio,proc,radio,camera,floppy,xgrp,scanner,uucp,fuse
```

Начиная с версии **0.5.0** поддерживается каталог **`/etc/role.d/`** — отдельные файлы для ролей.

### Утилиты командной строки

```bash
rolelst
rolelst -V
roleadd users fuse
roleadd -S users fuse
roleadd --file=test.role -m users radio camera floppy
roledel -S users fuse
roledel -Sr users
```

**Примечание.** Для администрирования ролей в графике доступен модуль ЦУС «Управление ролями» — альтернатива **`roleadd`** / **`roledel`** / **`rolelst`**.

### Связь с `control`

Включение и отключение подсистемы:

```bash
control libnss-role enabled
control libnss-role disabled
control libnss-role
```

### Сравнение с другими дистрибутивами

**`libnss-role`** и файл **`/etc/role`** — часть модели **Альт Линукс**. В **РедОС** и **Астра Линукс** в базовом курсе опираются на **плоские POSIX‑группы** и прямое членство пользователей в группах без того же механизма.

## 10. Итоговая картина — три уровня управления привилегиями

В **Альт Линукс** удобно мыслить **тремя уровнями**, которые дополняют друг друга:

| Уровень | Инструмент | Что настраивает | Только Альт Линукс |
|---------|------------|-----------------|-------------------|
| 1 — Роли | **`libnss-role`**, **`/etc/role`**, **`/etc/role.d/`** | Наследование привилегий через роли | Да |
| 2 — Системные утилиты | **`control`**, **`/etc/control.d/`** | Режимы доступа к SUID‑бинарникам и связанным объектам | Да |
| 3 — Приложения | **Polkit**, **`/etc/polkit-1/rules.d/`** | Авторизация действий приложений | Нет (стандарт Linux / freedesktop) |
| Дополнительно | **`sudo`**, **`/etc/sudoers`** | Запуск команд от root | Нет (стандарт) |

**Итог модуля.** Администратор **Альт Линукс** оперирует не только **Polkit** и **`sudo`**, но и **`control`**, и **модулем ролей** — в связке с **ЦУС** это даёт предсказуемую модель для рабочей станции и сервера. Понимание всех уровней — ключевое отличие специалиста по **Альт Линукс** от переноса только общелинуксовых привычек без учёта дистрибутива.

Быстрая диагностика Polkit:

```bash
pkaction --action-id <идентификатор_действия> --verbose
journalctl -u polkit --since today
ls /etc/polkit-1/rules.d/
```
